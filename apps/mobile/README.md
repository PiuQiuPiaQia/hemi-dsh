# Hemi DSH Mobile (iOS shell)

English | [中文](README.zh.md)

A native iOS shell that pairs with a Hemi DSH Host on the same Wi-Fi and shows that Host's full Web UI in a `WKWebView`. First version: connect flow (QR scan or pasted invitation, automatic reachable-address selection, one automatic pair request, six-digit verification code, explicit host approval), pinned TLS, and a native WebSocket bridge for the page's `window.__DSH_TRANSPORT__` contract. No React, no Capacitor, no Node dependencies.

## Layout

- `Package.swift`, `Sources/HemiMobileCore/` — pure-Swift protocol and policy logic: invitation parsing, leaf pinning, pairing client, pairing intake and request-deadline policies, origin rules, bridge script, Keychain store. Unit-tested on the host.
- `Tests/HemiMobileCoreTests/` — XCTest coverage for the injected socket bridge and shell control script in JavaScriptCore, pairing protocol fields, and real pinned-WSS connections (open→send→echo→close, redirect refusal, wrong pin, and server-observed teardown) against a local self-signed TLS fixture.
- `ios/App/` — UIKit app (`ai.hemi.dsh.mobile`, display name "Hemi DSH"): connect screen, scanner, remote Web UI screen, native socket bridge, and the shell control script.
- `experiments/wk-tls-trust/` — the WKWebView self-signed trust experiment with its verdict ([README](experiments/wk-tls-trust/README.md)).
- `scripts/` — build and test entry points, all executed on this machine before being documented here.

## Pairing protocol (kind `hemi-dsh-mobile`, version 1)

The invitation carries `{kind, version, origin, fingerprint, token, expiresAt}` and may add an `origins` array with more addresses of the same host; `fingerprint` is the lowercase-hex SHA-256 of the server leaf certificate DER. Scanning or pasting a multi-address invitation probes the candidates once and automatically picks the reachable address (`PairingClient.resolveInvitation`); the single pair POST, the status polls, the approved session, the remote WebView, and its sockets all use that chosen address, and a saved session re-picks before the remote screen opens (`PairingClient.resolveSession`), probing every probeable saved address — a single saved address included, and when `candidateOrigins` is absent or unparseable the stored origin is parsed under the same candidate rules — so a stale address is learned unreachable in seconds before the credentialed exchange; resolution only confirms or reorders known addresses (never the pin, the secrets, or new addresses), stores the chosen origin first in `candidateOrigins`, and keeps the legacy single-address storage when that field was absent. The client `POST /mobile/pair` sends `{version, invitationToken, requestId, deviceName, secret}` and receives `{requestId, verificationCode, status:'pending', expiresAt, serverName}`; it polls `POST /mobile/pair/status` (`{requestId, secret}`), and after approval exchanges `GET /mobile/session` (Bearer `<deviceId>.<secret>`) for the `__Host-hemi-mobile` HttpOnly cookie that authenticates every page request. ZCode's phone remote-control implementation uses a cloud relay; this shell keeps direct, pinned TLS connections to the local Host and sends no traffic through that relay. Server-side details live in `packages/hemi/mobile-access`.

## Security model

- TLS: every native connection and every WKWebView challenge goes through the same leaf-pin evaluation (`TLSPin.swift`): pin must match, anchor only to the pinned leaf, SSL host policy, no network fetch during evaluation. A mismatch fails closed and clears the pairing; trust returns only through a new invitation.
- Secret handling: `deviceId`/`secret` live in the Keychain (`WhenUnlockedThisDeviceOnly`) and in the HttpOnly cookie installed into the WKWebView cookie store. They are never injected into page JavaScript.
- Bridge scope: `window.__DSH_TRANSPORT__` (`createWebSocket` + `streamBaseUrl`) is injected at document start, main frame only; commands from subframes or foreign origins are dropped before reaching native code. WebSockets open only `wss://` on the paired host and port, carrying the cookie header on a pinned `URLSessionWebSocketTask`. The shell control global `window.__HEMI_MOBILE__` (`version`, `serverName`, `disconnect`) is injected the same way: frozen and read-only, carrying no origin, secret, or token, with `serverName` JSON-encoded so page-controlled text cannot inject script; its `disconnect` posts one fixed message that native routes only after the same main-frame and origin guard, so the Web settings page can close the remote screen while the pairing stays in the Keychain. The same script installs one owned `<style>` element (`hemi-mobile-scroll-style`, marked `data-hemi-mobile="scroll"`) into the served document — once, at DOMContentLoaded, because the document-start injection has no head yet, and idempotent on re-injection — carrying only the shell's scroll-containment CSS.
- Navigation: main-frame navigations stay in-app only for the paired origin; external links open in Safari; subframes load only same-origin. The remote screen hides the native navigation bar and aligns the WebView to the safe area, so connection information and disconnect live in the served Web settings page; the system back gesture and the overlay's back button remain as escape hatches. The outer WebView and connect screen do not rubber-band at their bounds, and the owned style sheet sets `overscroll-behavior-y: none` on the served app's conversation scroll host (`[data-conversation-scroll]`) and the outer `html`/`body` chain, so momentum at the transcript ends cannot bounce inside the chat flow; no wildcard selectors, no touch interception, and in-page nested scrollers and text areas keep their own behavior. Long content remains scrollable.
- Failures: a parsed invitation starts exactly one pairing attempt automatically — intake runs in the presenting modal's dismiss completion, and delivering the same invitation again while an attempt is live keeps that attempt instead of sending another pair POST; invitation tokens decide identity, so a re-scan of the original QR after origin resolution still keeps the live attempt. Each attempt sends exactly one pair POST, and its requestId, secret, and chosen origin are kept before that POST. An unknown POST outcome — an interrupted request, a transport failure, a budget expiry, or a 2xx answer the protocol rejects — keeps the attempt: the screen shows a local checking state and only polls status on the chosen origin, never switching addresses or re-sending the pair; a new POST requires the attempt to end by explicit rejection, expiry, the user abandoning it, or a new invitation with a different token. A failure during origin resolution sends nothing, so the screen offers one safe retry. Every protocol request — the session exchange included — carries the same fixed 15-second budget (per-request timeout plus a whole-request resource bound set on the client's owned configuration copy; a caller-shared configuration object is never mutated), so an unreachable address settles in seconds instead of the system-default minute; a timed-out or cancelled exchange clears nothing and sends nothing further, and cancellation surfaces as `CancellationError`. Other unknown network outcomes are shown and never retried automatically; only the idempotent status poll repeats (2 s start, +0.5 s growth, 5 s cap, +2 s on 429), ending at the server-reported request deadline — the invitation's own expiry never ends a live request, and a receipt-less attempt never times out locally. A probe with no answering candidate fails typed as unreachable (a case with no detail string, so nothing address- or credential-shaped can leak), and timeouts render with the shared-Wi-Fi hint plus retry and back actions instead of an open-ended spinner. Revocation (401) and certificate change ask for a new invitation.
- Lifecycle: a cold start with a stored pairing connects once on the connect screen's first appearance, probing the saved address credential-free first (a single saved address included) so a stale or unreachable address settles on the connect screen with the shared-Wi-Fi hint and the scan actions intact instead of holding the remote screen open, and the saved-connect offers a cancel that fences the running task's ticket and resets the state; returning from the remote screen — by back gesture, explicit disconnect, or fail-closed — never auto-reconnects, and backgrounding still keeps the remote page, its drafts, and scroll position while the in-page DSH ConnectionController owns reconnecting through the bridge. Forgetting the device closes sockets, removes the user script and message handler, stops loading, deletes the cookie, awaits the deletion, and clears the Keychain entry; the back gesture triggers the same quiescent teardown, and a cancelled bootstrap can no longer install cookies or load pages. While the remote screen's bootstrap loads or has failed, its overlay carries a back button on the same disconnect path — the pairing stays in the Keychain, only the screen closes — so the system back gesture is never the only exit.

## Build and test

```sh
cd apps/mobile
./scripts/test-core.sh            # shared logic and real pinned-WSS tests
./scripts/build-simulator.sh      # iphonesimulator compile + link, unsigned
./scripts/build-device-unsigned.sh  # generic iOS device compile + link, unsigned
```

The scripts allocate fresh temporary build directories, including the Swift test scratch path, so copied worktrees do not reuse SDK-bound module caches. Open `ios/App/App.xcodeproj` in Xcode for development; `ios/debug.xcconfig` optionally includes a user-owned `signing.local.xcconfig` for local signing overrides — the include reads that file when it exists, so keep it local and never commit it.

## Borrowed code

The QR scanner, the Keychain store pattern, and the pinned-TLS verification are adapted from the previous Hemi mobile shell (MIT, © 2026 PiuQiuPiaQia): `HemiScannerController` (old `HemiBotPlugin.swift` lines 243-281), `HemiKeychainStore` (old `HemiDeviceClient.swift` lines 45-62), and `hemiPinnedTLS` (lines 82-99). The old `flow.*` protocol, P256 bot signatures, and the hand-written HTTP/1.1 Content-Length parser are deliberately not carried over; URLSession handles DSH's multipart and streaming responses natively.

## Known limitations and device gaps

- A development-signed build has been installed and launched on iPhone 17 Pro Max. The user completed pairing, and the existing desktop Host reports the phone connected. A later "stuck connecting on cold start" report was traced to the Host's address changing (different subnet) while the saved session still pointed at the old, now unreachable address: recovery held the credentialed session exchange open with no exit in the overlay. This build makes that path fail fast and cancellable (credential-free probe including a single saved address, fixed request budget, overlay back button, saved-connect cancel), but recovery against a genuinely unreachable host still needs real-device acceptance on the new build.
- Asset catalogs cannot compile without a simulator runtime (actool needs simulator services), so `Assets.xcassets` is excluded from the target. The borrowed app icon ships through the legacy `CFBundleIcons`/`CFBundleIconFiles` entries with pre-rendered PNGs in the bundle (no actool dependency, no new artwork); its rendering on a home screen is not yet verified on a device.
- Device installation requires a matching development profile, Developer Mode, and explicit developer trust. The separate bundle id `ai.hemi.dsh.mobile` does not replace the old `ai.hemi.mobile` app; a development signature expires according to its profile.
- Cancelling a pending pair stops the client poll only; the protocol has no cancel endpoint, and the invitation expires server-side.
- The remote screen has no in-page error surface of its own yet: page-visible failures surface through the DSH Web UI, and native failures through the overlay and alerts.
- Usage-description strings in `Info.plist` are single bilingual strings; per-locale `.lproj` splits are deferred.
- Pairing UI keeps the code comparison and safe status confirmation but does not display IP, certificate, or expiry diagnostics in the normal flow. Transport failure logs contain protocol paths and system error identities, never invitation or credential bytes; a stopped poll does not show a busy spinner.
- The remote screen draws no native navigation: the bar is hidden while the screen is on top and restored for the connect screen, and connection information with Disconnect moved into the served Web settings page through `window.__HEMI_MOBILE__`. Safe-area rendering without the bar, keyboard overlap, cold-start auto-connect, the in-page disconnect, and the transcript-end scroll containment still need real-device acceptance.
